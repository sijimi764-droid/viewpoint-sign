# Warehouse Viewpoint Sign System 要件定義 正本 v1.0

**文書状態：BASELINE**  
**基準日：2026-09-01**  
**次工程：PoC-A 詳細設計**  
**原則：本書の確定事項は、新たな根拠またはHuman Gate判断なしに変更しない。**

## 1. 目的

倉庫内の壁・柱・棚側面など、奥行きや位置の異なる複数の既存平面へ印刷物を貼り、指定された視認範囲から見ると一つの文字・サインとして認識できる表示物を自動設計する。

代表ユースケースは `GA`、`GA-01-02` 等の倉庫ロケーション表示。単一視点でのみ完全形になる芸術的アナモルフォーシスではなく、歩行者・フォークリフト等が移動しながら広い範囲で識別できる実用サインを目的とする。

## 2. 最上位設計原則

優先順位は次のとおり。

**可読性 → 可読範囲 → 施工誤差耐性 → 既存面活用 → 施工容易性 → 希望サイズ・位置 → 近距離での外観**

要求条件で成立しない場合は単に不可能とせず、サイズ縮小、位置移動、字間・ストローク変更、使用面変更、重複投影、必要に応じた補助面追加などの成立案を自動探索して提示する。

## 3. Human Gate確定事項

| HG | 判断 | 確定内容 |
|---|---|---|
| HG-01 | B | 一点視点の完全性より広い視認範囲での可読性を優先 |
| HG-02 | B拡張 | 補助面を許可。ただし既存面のみのサイズ・位置変更案等も必ず探索 |
| HG-03 | B | ブラウザ型ではなくPC＋スマートフォン連携。ローカル／オフライン主体 |
| HG-04 | File | USB直接接続は使用しない。案件ファイルによる受け渡し |
| HG-05 | B | 基準マーカーは複数使用を推奨。通常2～3枚、1枚でも使用可能 |
| HG-06 | 仮確定 | 製品は印刷媒体非依存。PoCはA4普通紙から開始 |
| HG-07 | B | 可読範囲拡大のための重複投影を許可 |
| HG-08 | A+B | 背景付き矩形シートを標準。透明ラベル等はオプション |

## 4. 対象施工面と座標系

MVPは平面のみを扱う。対象は壁、柱側面、ラック側面、棚板側面、パネル等。曲面・円柱・自由曲面は初期対象外。

各施工面は3D四辺形 `P0..P3` として表現する。内部座標系は床面XY、高さZ。ユーザーにXYZを直接入力させることは基本としない。

## 5. 表示文字

初期MVPは `A-Z`, `0-9`, `-`。代表テスト文字は `GA`。文字はフォント文字列ではなくベクトルアウトラインへ変換して幾何処理する。

`GA-01-02` 等の長い表示では、遠距離 `GA`、近距離 `01-02` の二階層表示を標準提案可能とする。ユーザー要求時は全文字列投影も可能とする。

## 6. Viewing Zone

単一観察点ではなく Viewing Zone を設定し、複数サンプル視点へ展開する。歩行者・フォークリフト運転席等の複数目線高さを扱える。

視認ゾーンは均等とは限らず、入口側重視等の重要度を持てる。MVPでは「均等」「入口側重視」「近距離重視」等のプリセットを基本とする。

## 7. 投影・Gap・重複投影

目標文字ベクトルを観察位置から各施工平面へ逆投影し、どの面のどこへ何を貼るかを計算する。

投影先に施工面が存在しない領域は Gap として扱い、欠落面積、ストローク連続性、文字識別への影響を評価する。

複数視点で可読性を維持するため、必要に応じて同一ストロークの一部を複数面へ配置する重複投影を許可する。ただし、単純投影 → 弱い視点検出 → 欠落ストローク特定 → 必要部分だけ追加投影 → 再評価の順で行い、効果が小さい重複は採用しない。

## 8. 制約と探索

入力条件は `MUST / PREFER / FREE` に分類する。文字列はMUST。サイズ・位置・既存面のみ等は通常PREFERだが、明示固定時はMUSTへ昇格する。

標準探索順：

`L0 希望条件そのまま → L1 位置変更 → L2 サイズ変更 → L3 位置＋サイズ → L4 字間・ストローク等 → L5 使用施工面変更 → L6 重複投影 → L7 補助面追加`

補助面は最終手段とし、必要な場合は寸法・位置まで具体提案する。

## 9. 最適化方式

単一総合スコアだけで決定しない。

1. Hard Constraints：違反候補を除外
2. Feasibility：最低可読性、視認範囲、施工誤差耐性等を確認
3. Ranking：可読性、可読範囲、誤差耐性、既存面活用、施工容易性、重複量、希望サイズ、希望位置、外観等で順位付け

施工複雑度にはシート数、接合数、施工面数、補助面積、要求位置精度等を含める。極端な施工精度を要求する案は避ける。

## 10. 施工面属性

施工面は「使用可／使用非推奨／使用禁止」、施工性は「施工容易／通常／施工困難」等を設定可能とする。消防設備、操作盤、既存安全表示等を覆う面は人間が禁止指定できる。安全判断をAIだけに委ねない。

## 11. 候補提示

原則上位3案程度を提示する。例：推奨、サイズ優先、最大可読範囲。各案について可読範囲、サイズ、位置変更、使用面、重複量、補助面、印刷枚数、施工難易度、理由を表示する。

不成立時も単に「作成できません」とせず、原因と成立案を定量的に示す。

## 12. 印刷・施工

小さな断片を大量に切って貼る方式を避け、可能な限り大きな連続矩形シートとして印刷する。A4一枚に収まれば一枚、収まらなければA4/A3複数枚へ分割する。

ページ分割ではページ数、接合数、重要ストローク、空白位置を考慮し、可能なら重要な文字線途中を避ける。

施工PDF各ページには、案件名、施工面ID、シート番号、上下左右、隣接シート、位置合わせマーク、切断線、重ね線、施工基準位置、100mm校正線、1:1印刷表示を入れる。

標準重ね代初期値候補は10mm。施工面ごとに左端・下端等からの貼付基準位置を明示する。

背景付き矩形シートを標準とし、MVPは白背景＋黒文字。透明媒体等は将来オプション。

## 13. PrintProfile

印刷条件は投影エンジンから分離し、`paperSize`, `orientation`, `printableMargin`, `overlap`, `calibrationFactor`, `mediaType` 等を保持する。

100mm校正線を使ってプリンタ縮尺誤差を確認・補正できる構造とする。

## 14. Windows / Android構成

Windows MVP第一候補は C# / .NET / WPF。UIと Geometry / Projection / Readability / Optimization / Print / Project File 各エンジンを分離する。3Dレンダラーも計算ロジックから分離する。

Android側はXperiaを含むネイティブAndroidアプリを基本とし、観測・測定を担当。PC側は設計・最適化・印刷を担当する。

LiDARは必須とせず、通常カメラ＋基準マーカーで成立する設計を基本とする。

## 15. 基準マーカーと現場測定

アプリ自身が印刷用マーカーを生成する。各マーカーは固有ID、実寸、方向、原点を持つ。通常2～3枚推奨、1枚でも使用可能だが精度不足時は追加を要求する。

カメラ推定値を絶対視せず、ユーザー実測値を強い拘束条件として追加できる。施工面ごとに `Confirmed / Estimated / Low Confidence / Invalid` 等の品質状態を保持する。

## 16. PC⇔Xperia連携と案件ファイル

USB直接接続は使用しない。ファイルベース連携とし、転送手段はアプリから分離する。

案件ファイル仮称は `.wsa`（Warehouse Sign Anamorphosis）。ZIPコンテナ型とし、`manifest.json`, `environment.json`, `markers.json`, `measurements.json`, `camera/`, `preview/` 等を格納可能とする。

写真なしでもPC側でGeometryを再構成できることを必須とする。

## 17. 再現性・Geometry Lock

案件にはGeometry、制約、アルゴリズムバージョン、PrintProfile、選択Solution、Geometry Revision等を保存する。同一バージョン・同一入力から同一結果を再生成できることを目標とする。

設計確定時にGeometryをロックし、ロック後に寸法変更があれば既存Solution/PDFを無効として再計算を要求する。

## 18. セキュリティ

主要機能はインターネット不要。外部クラウド・AI APIを必須にしない。自動アップロードを行わない。テレメトリを必須にしない。現場画像は任意。EXIF等不要情報を除去可能とする。

`.wsa` 読込時はサイズ制限、JSON検証、ZIP安全展開、Path Traversal防止、破損検出等を行う。

AIによる施工面検出等は補助に限定し、人間が修正可能かつAIなしでも成立できることを基本とする。

## 19. MVP UI

基本4画面：`PROJECT / ENVIRONMENT / DESIGN / OUTPUT`。

PROJECTは文字・案件設定、ENVIRONMENTは施工面・寸法・Viewing Zone、DESIGNは位置・サイズ・候補生成、OUTPUTは候補比較・3D確認・PDF生成を担当する。

## 20. PoC-A

最初にカメラを作らず、完全な手入力Geometryで投影原理と印刷施工を検証する。

最低テスト：

- TEST-01 単一平面：普通の看板と同じ結果になること
- TEST-02 平行な複数平面：奥行きの違う3平面で `GA` が成立すること
- TEST-03 角度の異なる複数平面：柱・棚・壁を模した配置で `GA` が成立すること

生成した施工面図柄を同一カメラモデルから再レンダリングした場合、元の目標 `GA` と一致することを自動テストする。

## 21. PoC-B

PoC-Aと同じ物理環境をXperia＋マーカーで測定し、手入力した正解Geometryと比較する。カメラ測定誤差を分離評価する。

## 22. 実物試験と可読性

基準位置、左右±0.5m、左右±1.0m、前後、複数目線高さ等で撮影・人間評価を行う。正しく読めるか、誤読しないか、認識時間、設計評価との一致を確認する。

可読性PASS閾値は事前に固定せず、PoCの設計評価と人間評価の相関から決定する。

## 23. 開発Gate

`G0 数学単体試験 → G1 仮想再投影PASS → G2 PDF寸法PASS → G3 PoC-A物理施工PASS → G4 複数視点最適化PASS → G5 Androidマーカー測定PASS → G6 PoC-B PASS → G7 PC/Xperiaファイル連携PASS → G8 実倉庫試験`

**G3を通過するまでAndroid本格実装を開始しない。**

## 24. MVP Definition of Done

`GA入力 → 3つ以上の施工平面設定 → Viewing Zone設定 → 自動逆投影 → 成立性診断 → サイズ・位置等の自動代替案 → 複数視点評価 → 3Dプレビュー → A4原寸分割 → 施工PDF → 実際に印刷 → 物理面へ施工 → 指定範囲からGAと判読`

までを第一段階MVPの完成条件とする。

## 25. MVP非対象

曲面、円柱、日本語、任意画像、写真、ロゴ、LiDAR必須処理、クラウド同期、Webアプリ、複数の異なる文字を視点別に表示、Androidでの最適化、AI必須処理、大判プリンタ専用機能は後回しにする。

本書を真実源として開発を継続する。確定済みHuman Gate HG-01～08を再質問・再解釈しない。まずPoC-Aの詳細仕様、数学モデル、データ構造、テストケース、受入条件、実装構成を確定し、その後G0→G1→G2→G3の順で進める。高確信度かつ手戻り影響の小さい事項はAIが判断して進め、Human Gateが必要な事項だけユーザーへ確認する。単に「次へ進めてよいか」は確認しない。
